# Архитектурные решения (ADR)

В этом документе зафиксированы ключевые инженерные и архитектурные решения, принятые в ходе миграции портфолио на Next.js, Feature-Sliced Design и next-intl.

---

## ADR-001: Переход на Next.js App Router (16+)

### Контекст
Исходное приложение работало на базе Vite и React Router как классический SPA. Основные ограничения:
- Отсутствие серверного рендеринга (SSR/SSG), что ухудшало первичное отображение, SEO и индексацию страниц проектов.
- Сложность добавления серверных источников данных (обращение к API репозиториев, базам данных или headless CMS) без клиентского запроса и водопада загрузки.

### Решение
Выбран Next.js 16 на базе архитектуры **App Router**:
- Использование Server Components для страниц (`app/[locale]/page.tsx`, `app/[locale]/project/[id]/page.tsx`) со статической генерацией маршрутов (`generateStaticParams`).
- Изоляция клиентской интерактивности через директиву `'use client'` только для компонентов с состоянием, анимацией или обращением к DOM API.
- Сохранение серверного runtime (без `output: 'export'`) для будущей динамической интеграции внешних источников данных.

### Последствия
- Улучшена производительность первичной загрузки: HTML отдается предсобранным с актуальным контентом.
- Необходимость строгой дисциплины разделения серверного и клиентского кода.

## ADR-002: Организация кодовой базы по Feature-Sliced Design (FSD)

### Контекст
В исходной версии кодовая база имела плоскую структуру (`src/components/`, `src/data/`, `src/context/`), что приводило к сильной связанности модулей, циклическим импортам и затрудняло масштабирование.

### Решение
Принята методология Feature-Sliced Design со следующей иерархией слоёв:
```text
src/
  _app/       # Провайдеры, глобальные обёртки, i18n
  _pages/     # Композиция страниц (Home, Project, NotFound)
  widgets/    # Крупные блоки (Header, Hero, Skills, Projects, Contact, Footer)
  features/   # Сценарии пользователя (switch-language, switch-theme)
  entities/   # Предметные сущности (project)
  shared/     # Переиспользуемый базис (ui, lib, config, styles, assets)
```

**Правила зависимостей:**
1. Однонаправленный поток сверху вниз: `_app → _pages → widgets → features → entities → shared`.
2. Слайсы одного слоя не импортируют друг друга напрямую; композиция выполняется на вышестоящем слое.
3. Внешний доступ к слайсу разрешен строго через публичный API (`index.ts`, `index.server.ts`).
4. Автоматический контроль соблюдения правил возложен на `eslint-plugin-boundaries` и скрипт `tests/architecture.test.mjs`.

### Последствия
- Модули изолированы, архитектура предсказуема и легко расширяема.
- Исключены циклические зависимости.

## ADR-003: Маршрутизация и локализация через next-intl

### Контекст
В Vite использовался `react-i18next`. Язык хранился в `localStorage`, не отражался в адресной строке и сбрасывался при полной перезагрузке страницы. При этом теги разметки в сообщениях 404 использовали формат `<0>code</0>`, а тексты содержали фигурные скобки `{ ids, items }`, вызывающие синтаксические конфликты в парсерах ICU.

### Решение
1. **Префиксы маршрутов:** локали зафиксированы в URL (`/en`, `/ru`, `/uz` и `/{locale}/project/{id}`). Старые адреса перенаправляются редиректами 307/308 с сохранением query-параметров.
2. **Форматирование ICU:**
   - Числовые теги вида `<0>` заменены на именованные rich-text теги `<code>`.
   - Литеральные фигурные скобки в контенте Store защищены от парсинга ICU.
   - Корректность всех локалей гарантируется тестом `tests/messages.test.mjs`.
3. **Бесшовное переключение:** переключатель языка сохраняет текущий маршрут проекта и вертикальное положение прокрутки (`scrollY`).

### Последствия
- Поисковые системы корректно индексируют языковые версии.
- Пользователь может делиться прямой ссылкой на конкретную языковую версию страницы или проекта.

## ADR-004: Изоляция серверного слоя доступа к данным проектов

### Контекст
В исходной версии данные о проектах лежали в общем клиентском файле `src/data/projectsData.ts`. Для будущего подключения внешнего API (GitHub, BaaS) необходимо было изолировать источник данных от UI.

### Решение
В слое `entities/project` реализовано четкое разделение ответственности:
- Модели данных вынесены в `src/entities/project/model/types.ts`.
- Серверные функции `getProjects(locale)` и `getProject(id, locale)` размещены в `src/entities/project/api/get-projects.ts` и защищены пакетом `server-only`.
- Публичный API разделен на:
  - `index.ts` — клиентский экспорт (типы и UI-компоненты `ProjectCard`, `BenefitCard`).
  - `index.server.ts` — серверный экспорт (`getProjects`, `getProject`, `ProjectSourceError`).
- Server Components страниц запрашивают данные на сервере и передают клиентским виджетам сериализуемые пропсы.

### Последствия
- Клиентские бандлы не содержат лишней серверной логики и секретов.
- Подключение базы данных или внешнего API потребует изменений исключительно внутри `entities/project/api`, не затрагивая виджеты и страницы.

## ADR-005: Управление темой без FOUC и рассинхронизации гидратации

### Контекст
При SSG сервер не знает сохранённую тему пользователя в `localStorage`. Наивная реализация даёт вспышку неверной темы (FOUC) или рассинхронизацию гидратации. Дополнительно при смене locale React заменяет `<html>` и может удалить `data-theme`, если атрибут не был частью серверного JSX.

### Решение
1. **Тёмная тема — CSS-дефолт.** Отсутствие `data-theme` трактуется как `dark` во всех theme-dependent селекторах. В `<head>` выводится критический инлайн-CSS с тёмным фоном и `color-scheme: dark`, чтобы первый кадр не зависел от загрузки внешнего stylesheet.
2. **Блокирующий `ThemeScript`.** Инлайн-скрипт в `<head>` root layout выполняется до первого paint: читает `localStorage`, затем cookie `theme`, и выставляет `data-theme` + `color-scheme` на `<html>`. Серверные `cookies()`/`headers()` не используются, SSG сохраняется. На клиентской навигации скрипт рендерится как инертный `text/plain`, поэтому React не выполняет его повторно.
3. **`ThemeProvider` на `useSyncExternalStore`.** Источник истины — атрибут `data-theme` на `<html>`, `getServerSnapshot()` возвращает `dark`. Подписка на `MutationObserver` (только синхронизация состояния, без принудительного восстановления) и `storage` обновляет UI, включая межвкладочные изменения. Cookie `theme` — зеркало `localStorage` на случай его недоступности.
4. **Восстановление при смене locale.** Layout-effect до paint восстанавливает сохранённую тему, если React заменил `<html>` и удалил атрибут. Это устраняет потерю светлой темы при переходе `/en` → `/ru`.
5. **Подавление transition до гидратации.** `html:not(.theme-ready) *` отключает переходы; `ThemeProvider` добавляет `theme-ready` после монтирования. Визуал `ThemeSwitch` привязан к `html[data-theme='light']`, а не к `:checked`, поэтому гидратация не вызывает визуального скачка.

### Последствия
- SSG остаётся статическим: нет динамического рендера из-за темы.
- Нет FOUC при холодном старте, reload и смене locale; нет прыжка `ThemeSwitch`.
- Удалены глобальные патчи `Element.prototype` и восстанавливающий `MutationObserver`; DOM больше не переопределяется.
- `localStorage` — основное хранилище, cookie — резервное зеркало.

## ADR-006: Визуальное регрессионное тестирование на базе Playwright Baseline

### Контекст
Основное требование миграции — абсолютное сохранение внешнего вида оригинального сайта на Vite. Ручной визуальной проверки было недостаточно из-за большого числа сочетаний тем, языков, разрешений экранов и анимаций.

### Решение
Разработана строгая методология визуального сравнения:
1. В отдельном worktree зафиксировано эталонное приложение и сняты 233 PNG-скриншота по матрице:
   - 5 маршрутов × 3 языка × 2 темы × 3 базовых разрешения (375px, 768px, 1440px).
   - Пограничные брейкпоинты адаптивности и интерактивные состояния.
2. Тестовый раннер `playwright.visual.config.ts` нормализует факторы нестабильности:
   - Остановка бесконечных анимаций (marquee, background gradients) на нулевом кадре.
   - Прогревочный снимок (dummy capture) для полной отрисовки слоев с `backdrop-filter`.
   - Заморозка системного времени для стабильного года в Footer.
   - Фильтрация субпиксельного шума растеризации Chromium (разница каналов ≤ 3, порог до 600 пикселей).
3. Новая версия (`candidate`) сверяется с неизменяемым эталоном `tests/visual/baseline/`.

### Последствия
- 100% гарантия отсутствия случайных визуальных сдвигов, изменений отступов, шрифтов и цветов.
- Защита от регрессий при дальнейшей разработке.

## ADR-007: Развёртывание на Netlify с серверным Runtime

### Контекст
Старая версия разворачивалась как статический SPA с правилом перенаправления в `public/_redirects`: `/* /index.html 200`. Это правило перехватывало бы маршруты Next.js и ломало серверную маршрутизацию.

### Решение
1. Файл `public/_redirects` удален.
2. Добавлен `netlify.toml` с явной директивой `command = "pnpm build"`, обеспечивающей автоматическую интеграцию с плагином Next.js на Netlify.
3. В `next.config.ts` не включен `output: 'export'`, что сохраняет серверный runtime и возможности гибридного рендеринга.

### Последствия
- Корректная обработка серверных редиректов (307/308), кастомных кодов состояния HTTP 404 и будущей динамической подгрузки данных.

## ADR-008: Замена Locomotive Scroll на Lenis

### Контекст
Locomotive Scroll 5 не даёт собственной логики скролла: это обёртка над Lenis, которая добавляет `data-scroll*`-атрибуты, CSS и собственный RAF-цикл. В проекте эти возможности не использовались, при этом пакет дублировал Lenis, тянул лишний клиентский код и создавал конфликт с Motion-прогрессом hero.

### Решение
1. **Прямой Lenis** (`lenis@1.3.17`, точная версия) вместо `locomotive-scroll` и `@types/locomotive-scroll`.
2. **Единый провайдер** `_app/ui/smooth-scroll.tsx`: `lerp: 0.1`, `smoothWheel: true`, `syncTouch: false`, `autoRaf: true`. Колесо сглаживается Lenis, мобильный тач остаётся нативным. `autoRaf` обязателен — без него Lenis не обновляется без ручного RAF-цикла. Якоря идут 1.2 с с `easeInOutCubic`, чтобы не было резкого старта.
3. **Мобильный тач нативный.** `syncTouch: false` сохраняет инерцию ОС и не ломает доступность; Lenis работает на всех ширинах.
4. **Один делегированный обработчик якорей.** Перехватывает `a[href^="#"]` на документе, уважает `defaultPrevented` (header обрабатывает свои ссылки сам), модификаторы и `target="_blank"`. `scroll-margin-top` из CSS (`--header-height`) передаётся Lenis как отрицательный offset; при отсутствии — измеряется `[data-header]`.
5. **`prefers-reduced-motion`.** Lenis не создаётся, навигация идёт нативным `scrollIntoView`/`window.scrollTo` без анимации.
6. **Сброс при смене маршрута.** `scrollToTop(true)` (immediate); hash сохраняется, только если цель существует на новой странице.
7. **`scrollbar-gutter: stable`** на `html` убирает горизонтальный сдвиг при появлении/исчезновении скроллбара, в том числе при якорной навигации.

### Последствия
- Удалены лишняя зависимость, её типы, CSS и неиспользуемая `data-scroll`-инфраструктура.
- Единая точка управления скроллом: `@/shared/lib` (`scrollToSection`, `scrollToElement`, `scrollToTop`, pause/resume).
- Мобильный тач остаётся нативным; reduced motion полностью отключает гладкий скролл.
- `overflow: hidden` на `main` и sticky-поведение секций не затрагивались.

## ADR-009: Строгая валидация и сегментная чистота Feature-Sliced Design (FSD 2.1)

### Контекст
В ходе аудита архитектуры были выявлены структурные отклонения от канонического FSD:
1. В слое `src/shared` находился каталог `theme` с внутренней структурой слайса (`model/`, `ui/`, `index.ts`), что противоречило спецификации FSD (в `shared` слайсы запрещены, допускаются только технические сегменты).
2. В слайсе `src/entities/project` сегмент `model` зависел от `api` (`asset-map.ts` импортировал `ProjectSourceError` из `api/project-source-error`), вызывая сегментную инверсию.
3. Линтер архитектурных границ `eslint-plugin-boundaries` не защищал от импорта серверных API (`index.server.ts`) клиентскими слоями (`widgets`, `features`, `entities`, `shared`).
4. Архитектурные тесты проверяли только моковые строки и не валидировали реальную кодовую базу.

### Решение
1. **Канонизация `shared`**: псевдо-слайс `src/shared/theme` расформирован. Состояние и хук `useTheme` перенесены в `src/shared/lib/theme/` (экспорт через `@/shared/lib`), а `<ThemeScript />` перенесён в `src/shared/ui/theme-script/` (экспорт через `@/shared/ui`). Слой `shared` содержит исключительно технические сегменты: `ui`, `lib`, `config`, `assets`, `styles`, `i18n`.
2. **Устранение сегментной инверсии**: `ProjectSourceError` перенесён в `src/entities/project/model/project-source-error.ts`, восстановив правильный поток зависимостей `api → model`.
3. **Строгая изоляция серверных данных**: в `scripts/fsd-config.mjs` настроено правило, блокирующее импорт `index.server.ts` для любых слоёв кроме `routes` (`app/**`) и `_pages`.
4. **Комплексные тесты**: матрица архитектурных тестов расширена до 23 тестов (включая запреты на кросс-импорты между слайсами одного слоя, глубокие импорты и проверку всех реальных файлов `src/**` и `app/**`).

### Последствия
- Полное соответствие спецификации FSD 2.1 без компромиссов и обходных путей.
- Гарантированная защита от случайной утечки серверного кода в клиентские бандлы на уровне CI/линтера.
- 100% покрытие архитектурных границ автоматическими тестами.

## ADR-010: Стандартизация скриншотов проектов и единый визуальный стиль

### Контекст
1. Ранее скриншоты проектов различались по стилю, геометрии и смысловому наполнению:
   - Проект `palma` содержал полные hero-экраны лендинга: десктопный (`1920x1080`) и мобильный (`390x844`).
   - Проект `store` содержал десктопный снимок произвольного разрешения (`2200x1268`), а мобильный скриншот (`880x1100`) представлял собой фрагмент каталога товаров с обрезанными наполовину карточками и без навигации/шапки.
2. При открытии полноэкранного режима мобильного скриншота Store отображалась только верхняя половина контента, а карточки товаров обрезались посередине. Кроме того, пропорции `880x1100` искажали вьюпорт и не соответствовали мобильному формату других проектов.

### Решение
1. **Единый композиционный стиль**: все скриншоты проектов фиксируют первый экран (above-the-fold hero landing) в тёмной теме (`dark`), содержащий брендовую шапку/навигацию, бэйдж/кикер, заголовок, подзаголовок и основные CTA-кнопки. Запрещены произвольные обрезанные фрагменты страниц или рассечённые карточки.
2. **Фиксированные разрешения и пропорции**:
   - Десктоп: строго `1920x1080` (пропорция 16:9 Full HD).
   - Мобильный: строго `390x844` (пропорция 9:19.5, стандарт современных iPhone).
   - Формат: неперемежающийся RGB PNG без искажений и сжатия с потерями.
3. **Синхронизация с галереей**: в `src/features/project-gallery/ui/project-gallery.tsx` константы `DESKTOP_IMAGE` (`1920x1080`) и `MOBILE_IMAGE` (`390x844`) приведены в соответствие с фактическими размерами ассетов, гарантируя правильное вычисление пропорций в Next.js `Image` и модальном просмотрщике `ImageViewer`.
4. **Правило в `AGENTS.md`**: зафиксированы строгие требования к скриншотам для будущих проектов.

### Последствия
- Полная визуальная консистентность между проектами `palma` и `store`.
- Устранены дефекты отображения в модальном просмотрщике и в адаптивном превью карточки проекта.
