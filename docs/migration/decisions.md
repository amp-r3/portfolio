# Архитектурные решения (ADR)

В этом документе зафиксированы ключевые инженерные и архитектурные решения, принятые в ходе миграции портфолио на Next.js, Feature-Sliced Design и next-intl.

---

## ADR-001: Переход на Next.js App Router (16+)

### Контекст
Исходное приложение работало на базе Vite и React Router как классический SPA. Основные ограничения:
- Отсутствие серверного рендеринга (SSR/SSG), что ухудшало первичное отображение, SEO и индексацию страниц проектов.
- Сложность добавления серверных источников данных (обращение к API репозиториев, базам данных или headless CMS) без клиентского запроса и водопада загрузки.

### Решение
Выбран Next.js 16 на базе архитектуры **App Router**:
- Использование Server Components для страниц (`app/[locale]/page.tsx`, `app/[locale]/project/[id]/page.tsx`) со статической генерацией маршрутов (`generateStaticParams`).
- Изоляция клиентской интерактивности через директиву `'use client'` только для компонентов с состоянием, анимацией или обращением к DOM API.
- Сохранение серверного runtime (без `output: 'export'`) для будущей динамической интеграции внешних источников данных.

### Последствия
- Улучшена производительность первичной загрузки: HTML отдается предсобранным с актуальным контентом.
- Необходимость строгой дисциплины разделения серверного и клиентского кода.

## ADR-002: Организация кодовой базы по Feature-Sliced Design (FSD)

### Контекст
В исходной версии кодовая база имела плоскую структуру (`src/components/`, `src/data/`, `src/context/`), что приводило к сильной связанности модулей, циклическим импортам и затрудняло масштабирование.

### Решение
Принята методология Feature-Sliced Design со следующей иерархией слоёв:
```text
src/
  _app/       # Провайдеры, глобальные обёртки, i18n
  _pages/     # Композиция страниц (Home, Project, NotFound)
  widgets/    # Крупные блоки (Header, Hero, Skills, Projects, Contact, Footer)
  features/   # Сценарии пользователя (switch-language, switch-theme)
  entities/   # Предметные сущности (project)
  shared/     # Переиспользуемый базис (ui, lib, config, styles, assets)
```

**Правила зависимостей:**
1. Однонаправленный поток сверху вниз: `_app → _pages → widgets → features → entities → shared`.
2. Слайсы одного слоя не импортируют друг друга напрямую; композиция выполняется на вышестоящем слое.
3. Внешний доступ к слайсу разрешен строго через публичный API (`index.ts`, `index.server.ts`).
4. Автоматический контроль соблюдения правил возложен на `eslint-plugin-boundaries` и скрипт `tests/architecture.test.mjs`.

### Последствия
- Модули изолированы, архитектура предсказуема и легко расширяема.
- Исключены циклические зависимости.

## ADR-003: Маршрутизация и локализация через next-intl

### Контекст
В Vite использовался `react-i18next`. Язык хранился в `localStorage`, не отражался в адресной строке и сбрасывался при полной перезагрузке страницы. При этом теги разметки в сообщениях 404 использовали формат `<0>code</0>`, а тексты содержали фигурные скобки `{ ids, items }`, вызывающие синтаксические конфликты в парсерах ICU.

### Решение
1. **Префиксы маршрутов:** локали зафиксированы в URL (`/en`, `/ru`, `/uz` и `/{locale}/project/{id}`). Старые адреса перенаправляются редиректами 307/308 с сохранением query-параметров.
2. **Форматирование ICU:**
   - Числовые теги вида `<0>` заменены на именованные rich-text теги `<code>`.
   - Литеральные фигурные скобки в контенте Store защищены от парсинга ICU.
   - Корректность всех локалей гарантируется тестом `tests/messages.test.mjs`.
3. **Бесшовное переключение:** переключатель языка сохраняет текущий маршрут проекта и вертикальное положение прокрутки (`scrollY`).

### Последствия
- Поисковые системы корректно индексируют языковые версии.
- Пользователь может делиться прямой ссылкой на конкретную языковую версию страницы или проекта.

## ADR-004: Изоляция серверного слоя доступа к данным проектов

### Контекст
В исходной версии данные о проектах лежали в общем клиентском файле `src/data/projectsData.ts`. Для будущего подключения внешнего API (GitHub, BaaS) необходимо было изолировать источник данных от UI.

### Решение
В слое `entities/project` реализовано четкое разделение ответственности:
- Модели данных вынесены в `src/entities/project/model/types.ts`.
- Серверные функции `getProjects(locale)` и `getProject(id, locale)` размещены в `src/entities/project/api/get-projects.ts` и защищены пакетом `server-only`.
- Публичный API разделен на:
  - `index.ts` — клиентский экспорт (типы и UI-компоненты `ProjectCard`, `BenefitCard`).
  - `index.server.ts` — серверный экспорт (`getProjects`, `getProject`, `ProjectSourceError`).
- Server Components страниц запрашивают данные на сервере и передают клиентским виджетам сериализуемые пропсы.

### Последствия
- Клиентские бандлы не содержат лишней серверной логики и секретов.
- Подключение базы данных или внешнего API потребует изменений исключительно внутри `entities/project/api`, не затрагивая виджеты и страницы.

## ADR-005: Управление темой без FOUC и рассинхронизации гидратации

### Контекст
При SSR/SSG сервер генерирует HTML без знания о сохраненной теме пользователя в `localStorage`. В наивной реализации это приводит либо к вспышке неверной темы (FOUC — Flash of Unstyled Content), либо к ошибкам гидратации React из-за несовпадения атрибутов и классов.

### Решение
1. **Ранняя установка темы до рендера:** в `<head>` подключается критический инлайн-скрипт `ThemeScript`, который считывает `localStorage.getItem('theme')` и мгновенно выставляет атрибут `data-theme` на теге `<html>`. По умолчанию (при отсутствии записи) выбирается `dark`.
2. **Синхронизация через `useSyncExternalStore`:** `ThemeProvider` использует стандартный хук React 18/19 для подписки на внешнее хранилище без вызова дополнительных ререндеров после монтирования.
3. **Обработка ограничений:** предусмотрен fallback для сред с заблокированным хранилищем (`SecurityError`), сохраняющий работоспособность страницы в темной теме.

### Последствия
- Отсутствуют визуальные вспышки и мерцания при переходе между страницами и холодном старте.
- Полная согласованность гидратации React.

## ADR-006: Визуальное регрессионное тестирование на базе Playwright Baseline

### Контекст
Основное требование миграции — абсолютное сохранение внешнего вида оригинального сайта на Vite. Ручной визуальной проверки было недостаточно из-за большого числа сочетаний тем, языков, разрешений экранов и анимаций.

### Решение
Разработана строгая методология визуального сравнения:
1. В отдельном worktree зафиксировано эталонное приложение и сняты 233 PNG-скриншота по матрице:
   - 5 маршрутов × 3 языка × 2 темы × 3 базовых разрешения (375px, 768px, 1440px).
   - Пограничные брейкпоинты адаптивности и интерактивные состояния.
2. Тестовый раннер `playwright.visual.config.ts` нормализует факторы нестабильности:
   - Остановка бесконечных анимаций (marquee, background gradients) на нулевом кадре.
   - Прогревочный снимок (dummy capture) для полной отрисовки слоев с `backdrop-filter`.
   - Заморозка системного времени для стабильного года в Footer.
   - Фильтрация субпиксельного шума растеризации Chromium (разница каналов ≤ 3, порог до 600 пикселей).
3. Новая версия (`candidate`) сверяется с неизменяемым эталоном `tests/visual/baseline/`.

### Последствия
- 100% гарантия отсутствия случайных визуальных сдвигов, изменений отступов, шрифтов и цветов.
- Защита от регрессий при дальнейшей разработке.

## ADR-007: Развёртывание на Netlify с серверным Runtime

### Контекст
Старая версия разворачивалась как статический SPA с правилом перенаправления в `public/_redirects`: `/* /index.html 200`. Это правило перехватывало бы маршруты Next.js и ломало серверную маршрутизацию.

### Решение
1. Файл `public/_redirects` удален.
2. Добавлен `netlify.toml` с явной директивой `command = "pnpm build"`, обеспечивающей автоматическую интеграцию с плагином Next.js на Netlify.
3. В `next.config.ts` не включен `output: 'export'`, что сохраняет серверный runtime и возможности гибридного рендеринга.

### Последствия
- Корректная обработка серверных редиректов (307/308), кастомных кодов состояния HTTP 404 и будущей динамической подгрузки данных.
