# Миграция: этапы 0–3

## Эталон

Исходный коммит: `1ba5927996ee783577c6d6c38ad69796f6afea4c`.
Окружение и SHA-256 исходного lockfile закреплены в [baseline.json](baseline.json).
Используются Node.js 24.15.0 и pnpm 10.33.3. Все команды выполняются из корня репозитория.

```bash
nvm use
pnpm install --frozen-lockfile
pnpm exec playwright install chromium firefox webkit
pnpm baseline:prepare
pnpm baseline:start
```

`baseline:prepare` создаёт detached worktree в `.worktrees/portfolio-baseline`, устанавливает его собственный lockfile, собирает и проверяет исходное приложение. Вывод сохраняется в `artifacts/baseline/{build,lint}.log`. `baseline:start` запускает production preview на http://127.0.0.1:4173 и проверяет SHA, чистоту checkout и контрольную сумму lockfile. Порт должен быть свободен. Эталон не использует зависимости основного приложения.

## Скриншоты и движение

```bash
pnpm baseline:capture
pnpm test:visual
pnpm baseline:record
```

Playwright самостоятельно запускает и останавливает preview; отдельно запущенный `baseline:start` перед тестами нужно остановить. Для сравнения закреплён Chromium из Playwright 1.64.1 на Ubuntu 24.04.4 LTS x64, DPR 1, timezone Asia/Tashkent, browser locale en-US. Дата фиксируется через `setFixedTime`, таймеры продолжают работать.

Основная матрица — 90 сочетаний: пять маршрутов, три языка, две темы и три viewport. Главная снимается в пяти положениях: Hero, Skills, Projects, Contact, Footer. Дополнительно снимаются граничные ширины, hover/focus, прокрученный Header и мобильное меню. Язык выбирается существующим переключателем. Селекторы не зависят от хэшей CSS Modules.

Перед статическими кадрами загружаются шрифты и изображения, завершаются reveal-анимации; бесконечные анимации ставятся на паузу в нулевой фазе. После каждой прокрутки изображения декодируются повторно, а перед сравниваемым кадром делается прогревающий снимок, чтобы Chromium успел отрисовать слои с `filter`/`backdrop-filter`. Видеозапись использует обычные анимации.

Сравнение допускает только субпиксельный шум растеризации между Vite и Next.js: разница отдельного канала до 3 уровней не считается значимой, допускается до 600 значимых пикселей, крайняя строка и столбец кадра игнорируются. Для двух эталонов открытого меню исключена устаревшая область с подписью языка; маски секций и других элементов не используются.

PNG находятся в `tests/visual/baseline` и сохраняются в Git. `baseline:capture` создаёт файлы исключительно с флагом `wx`: существующие эталоны не перезаписываются даже этой командой, а сравниваются с текущим кадром. Это позволяет возобновлять прерванную съёмку. `test:visual` не создаёт отсутствующие эталоны и не принимает новые снимки автоматически. При несовпадении сохраняются actual/expected/diff, overlay и trace в `artifacts/visual` и HTML-отчёт в `artifacts/visual-report`. Видео лежат в `artifacts/baseline/videos`, вне Git.

`VISUAL_TARGET=candidate pnpm test:visual` сравнивает локализованные адреса Next.js на порту 3000 с теми же эталонами. После этапа 3 полный прогон проходит: 141 проверка, один сценарий поведения исходной версии пропускается для candidate. Все 233 PNG сравнены без необъяснимых отличий.

## Исходные проверки и известные особенности

- `pnpm build` и `pnpm lint` проходят после frozen-установки. Vite предупреждает о JS-чанке больше 500 kB; это существующее предупреждение, не регрессия миграции.
- Без сохранённой настройки тема dark при обеих системных темах. Сохранённая тема влияет на desktop/mobile изображения проектов.
- В исходной версии язык по умолчанию en не отражался в URL и сбрасывался после полной загрузки страницы; после этапа 3 язык хранится в локализованном адресе.
- В исходной версии неизвестный проект и URL показывали интерфейс 404, но SPA preview отвечал HTTP 200; после этапа 3 возвращается HTTP 404.
- Якоря Header на странице проекта не переходят к секциям главной: целевые элементы отсутствуют.
- В исходной версии якоря Header использовали `history.pushState(null, ...)`; в новом приложении они переходят через next-intl navigation, проверки якорей и истории выполняются независимо.
- Возврат использует историю браузера; при прямом входе fallback на главную отсутствует.
- Логотипы с `href=""` перезагружают текущий адрес; в `mailto:` контакта сохранён лишний `}`.
- Кнопка меню не имеет доступного имени. Тест использует её структуру SVG; улучшение доступности не включено в миграцию.
- Код темы ищет глобальную `.gradientLayer`, тогда как градиентные слои имеют классы CSS Modules; предполагаемая остановка градиентов при переключении темы может не применяться.
- Footer присутствует только на главной. Для denied localStorage содержимое остаётся доступным; сообщения в console о невозможности сохранения настройки ожидаемы.

Эти особенности записываются как исходное поведение; их исправления требуют отдельных задач.

## Каркас Next.js и правила FSD

Используются Next.js / eslint-config-next 16.4.2, React / React DOM 19.3.1, next-intl 4.14.9; сохранены TypeScript 5.9.3, ESLint 9.39.1 и Sass 1.94.2. Версии зависимостей закреплены без диапазонов, установка воспроизводится через frozen lockfile. Библиотеки интерфейса сохранены на прежних версиях.

`app/` — адаптер Next.js. Зависимости FSD направлены `_app → _pages → widgets → features → entities → shared`, можно пропускать слои. Слайсы одного слоя не импортируют друг друга; в shared допускаются зависимости между техническими сегментами. Внутри слайса разрешены относительные импорты, снаружи — только публичный `index.ts`, `index.server.ts` или `index.client.ts`. `index.server.ts` создаётся вместе с серверным кодом, защищённым `server-only`; его нельзя реэкспортировать через общий клиентский barrel.

ESLint проверяет направление и публичные точки входа через `eslint-plugin-boundaries` 7.2.0 с TypeScript resolver. `pnpm test:architecture` проверяет 12 разрешённых и запрещённых импортов, включая относительные пути, алиасы, deep imports и обращения к legacy. Временные исключения legacy перечислены в `eslint.config.mjs`; TypeScript явно включает только новые слои, маршруты, конфигурацию и тесты. Исключения удаляются по мере переноса соответствующего кода.

## Маршруты, локализация и границы этапа 3

`app/[locale]/layout.tsx` — корневой layout. `generateStaticParams` создаёт `/en`, `/ru`, `/uz`; `dynamicParams = false` и `hasLocale` не пропускают неизвестную локаль. `src/_app/i18n/request.ts` получает локаль через `next/root-params` и загружает `messages/{locale}.json`, сохраняя статическую генерацию. Конфигурация next-intl: `localePrefix: 'always'`, `defaultLocale: 'en'`, `localeDetection: false`; `proxy.ts` подключает middleware.

Адреса: `/en`, `/ru`, `/uz` и `/{locale}/project/{id}`. Старые `/` и `/project/:id` отвечают 307/308 на `/en` и `/en/project/:id`; query сохраняется, hash — клиентским переходом. Неизвестная локаль `/de` переходит на `/en/de` и затем отдаёт 404 через `app/[locale]/[...rest]`. Неизвестный проект и неизвестный URL возвращают HTTP 404 с исходным экраном 404.

Сообщения переведены на ICU без редакторских изменений. Тег `<0>` в 404 заменён именованным `code`, литеральные фигурные скобки `{ ids, items }` сохранены как текст. `pnpm test:messages` проверяет структуру, ICU и эти литералы — 7 проверок. Переключатель языка сохраняет цикл `en → ru → uz`, маршрут проекта и положение прокрутки; ссылки и якоря используют навигацию next-intl.

Header находится в общем layout, Footer — только на главной. `not-found.tsx` и клиентский `error.tsx` — отдельные границы; для технической ошибки сохранён тот же экран 404, потому что отдельного исходного дизайна не было. Loader подключён только в `app/[locale]/project/loading.tsx`, без нового контейнера.

`/en`, `/ru`, `/uz` и шесть страниц проектов (`weather`, `store` × три языка) генерируются статически; catch-all остаётся серверным. React Router и i18next пока остаются в `package.json` до этапа 5, но новый код их не импортирует. Требуется `next start`; статический export не используется.

Корневой layout и страницы серверные. Маршрут проекта принимает `params: Promise<{id: string}>`, проверяет `ProjectId` (`weather | store`) и вызывает `notFound()` для неизвестного id; метаданные выполняют ту же проверку. Внешних API и дублирования полных данных проектов на этапе 3 нет.

Метаданные и Viewport API сохраняют содержимое исходного `index.html`. Все URL заданы явно; `metadataBase` не используется, чтобы Next.js не удалял завершающий `/` у исходного canonical URL. SPA catch-all `_redirects` удалён только в новой ветке. Редиректы локалей реализованы; настройка хостинга и публикация ещё не выполнялись.

Постоянные демонстрационные стили, новый reset, шрифты, тема, `next/image` и `next/font` в каркас не добавлены. Неперенесённые React Router / i18next остаются в зависимостях до этапа 5, но новым приложением не используются. Vite и его конфигурация удалены из активного приложения; эталонный worktree сохраняет собственный Vite.
