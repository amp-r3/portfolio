# План миграции портфолио на Next.js и FSD

## Цель и приоритеты

Перевести портфолио с Vite и React Router на Next.js App Router, организовать код по FSD, заменить i18next на next-intl и подготовить серверное получение проектов.

**Главный критерий: после миграции сайт должен выглядеть так же, как текущая версия.** Сохраняются композиция страниц, тексты, изображения, шрифты, размеры, отступы, цвета, адаптивность, светлая и тёмная темы, состояния элементов и характер анимаций.

Порядок приоритетов:

1. Визуальное соответствие и работоспособность существующего интерфейса.
2. Next.js, FSD и next-intl.
3. Серверный доступ к текущим данным через независимый от источника интерфейс.
4. Подключение GitHub или BaaS после стабилизации новой версии.

Статус: этапы 0, 1 и 2 выполнены и проверены в ветке `migration/next-fsd`. Этапы 3–6 ещё не начинались. Чекбоксы отмечаются только после проверки результата соответствующего этапа.

## Исходное состояние

| Область | Текущая реализация |
| --- | --- |
| Основа | React 19, TypeScript, Vite, pnpm |
| Маршруты | `/`, `/project/:id`, экран 404; React Router |
| Проекты | `weather` и `store` в `src/data/projectsData.ts` |
| Переводы | `react-i18next`, JSON в `public/locales/{en,ru,uz}/translation.json` |
| Стили | SCSS Modules, глобальные стили и токены в `src/styles` |
| Шрифты | Локальные Inter, Exo2 и Azonix |
| Тема | `data-theme` на `html`, localStorage, скрипт в `index.html`, ThemeProvider |
| Движение | Motion, Locomotive Scroll, react-fast-marquee, CSS-анимации |
| Развёртывание | В проекте есть SPA-правило Netlify в `public/_redirects` |

Особенности, которые нужно учитывать при переносе:

- `Header`, `SmoothScroll`, кнопки возврата и страницы связаны с React Router.
- Тема влияет на фоновые слои и набор скриншотов проектов, включая мобильные изображения.
- `active` и `scrolled` используются как глобальные классы внутри SCSS Modules.
- В сообщении 404 используется `Trans` с тегом `<0>…</0>`; формат нужно адаптировать для next-intl с сохранением выделения текста.
- Текущий код выбирает тёмную тему по умолчанию даже при светлой системной теме. Миграция должна сохранить это поведение; изменение политики темы — отдельная задача.
- Footer сейчас входит в главную страницу. Его перенос в общий layout не должен добавить его на страницы проектов или ошибок.

## Стратегия работы

- Выполнять миграцию в отдельной ветке этого репозитория, например `migration/next-fsd`.
- Перед началом сохранить ссылку на исходный коммит и воспроизводимый запуск старой версии. Для сравнения использовать отдельный checkout/worktree и другой порт.
- Собрать новый каркас Next.js и переносить готовые компоненты небольшими группами сразу в целевую структуру FSD.
- Каждый этап оформлять отдельными проверяемыми коммитами. Переходить к следующему этапу после устранения обнаруженных визуальных регрессий.
- Сохранять SCSS рядом с соответствующим UI. При переносе менять пути импорта, сохраняя CSS-правила и структуру DOM, от которой зависят селекторы.
- Не совмещать миграцию с редизайном, заменой UI-библиотек, изменением текстов, переименованием CSS-классов или массовым обновлением зависимостей.
- Оптимизации через `next/image`, `next/font`, изменение анимаций и переработку Sass выполнять отдельными задачами после приёмки визуального соответствия.

## Целевая структура

```text
app/                              # Маршруты и специальные файлы Next.js
  [locale]/
    layout.tsx
    page.tsx
    project/[id]/page.tsx
    not-found.tsx
    error.tsx
    loading.tsx
src/
  _app/                           # Провайдеры, композиция приложения, i18n
    providers/
    i18n/
  _pages/                         # Композиция страниц
    home/
    project/
    not-found/
  widgets/                        # Самостоятельные блоки страниц
    header/
    hero/
    skills/
    projects/
    contact/
    footer/
  features/
    switch-language/
    switch-theme/
  entities/
    project/
      api/                        # Серверные функции доступа к проектам
      model/                      # Типы и преобразования данных
      ui/                         # ProjectCard и UI сущности
      index.ts
      index.server.ts             # Отдельный экспорт серверного API
  shared/
    ui/
    lib/
    config/
    styles/
    assets/
messages/                         # Сообщения en, ru, uz для next-intl
public/                           # Статические файлы с публичными URL
```

Дерево показывает целевые области ответственности. Создавать папки и сегменты по мере появления кода. Корневые layout, обработку неизвестной локали и глобальные специальные файлы Next.js уточнить при настройке маршрутизации.

Правила зависимостей:

- Направление импортов: `_app` → `_pages` → `widgets` → `features` → `entities` → `shared`; можно пропускать промежуточные слои.
- Слайсы одного слоя не импортируют внутренности друг друга. Общую композицию выполнять на верхнем слое.
- Между слайсами использовать публичные экспорты; внутри слайса допустимы относительные импорты.
- `shared` не знает о сущности проекта и страницах. Низкоуровневое состояние темы может находиться в `shared`, переключатель — в `features`, подключение провайдера — в `_app`.
- Server-only код не экспортировать через общий клиентский barrel-файл. Получение данных отделить от UI и браузерных зависимостей.
- Существующий `ProjectDetails` можно оставить в `src/_pages/project/ui`, если он используется только этой страницей. Дополнительный widget нужен при реальной необходимости композиции или повторного использования.
- Локализацию Next.js разместить в `_app/i18n`; адаптеры навигации, необходимые нижним слоям, — в `shared`. Нижние слои не должны импортировать `_app`.

## Этап 6. Подключить GitHub или BaaS отдельной итерацией

Этот этап не блокирует выпуск архитектурной миграции. Решение об источнике данных пока открыто.

| Вариант | Когда выбирать | Что потребуется |
| --- | --- | --- |
| Файлы в GitHub | Контент удобно менять через Git | Явная схема JSON/MDX, переводы, ссылки на изображения, серверное чтение файлов |
| Метаданные GitHub API | Нужны сведения о репозиториях | Сопоставление с вручную подготовленными кейсами; метаданных недостаточно для текущего UI |
| BaaS | Нужны база, хранение изображений и редактирование данных вне репозитория | Схема, правила доступа, импорт контента и выбор интерфейса редактирования |

- [ ] Выбрать источник и способ редактирования контента; переносить существующие тексты и изображения без изменения отображения.
- [ ] Реализовать адаптер за существующими `getProjects` / `getProject`.
- [ ] Валидировать входные данные и преобразовывать их в внутреннюю модель проекта.
- [ ] Определить хранение локализаций, сортировку, обязательные поля и варианты изображений.
- [ ] Настроить явную стратегию кэширования и обновления. Для редко меняющегося контента не обращаться к внешнему API при каждом просмотре без необходимости.
- [ ] Определить поведение при timeout, недоступности источника, лимите API и некорректном ответе; по возможности сохранять последнюю корректную кэшированную версию.
- [ ] Серверные секреты хранить вне клиентских переменных окружения; описать необходимые переменные в примере конфигурации.
- [ ] Проверить успешный ответ, неизвестный проект, отказ источника и обновление кэша; повторить визуальное сравнение с тем же контентом.

**Готовность:** внешний источник заменяет локальный адаптер, сохраняя внешний вид и контракт данных.

| Границы адаптивности | Ширины на 1 px меньше, ровно и на 1 px больше 380, 400, 576, 640, 768, 992 и 1024 px |
| Header | Верх страницы, прокрученная страница, открытое/закрытое меню, блокировка прокрутки |
| Элементы | Hover на desktop, focus с клавиатуры, нажатие, ссылки и переключатели |
| Изображения | Светлые/тёмные и desktop/mobile варианты, пропорции и обрезка |
| Анимации | Появление Hero, параллакс, reveal секций, градиенты, marquee, смена темы, smooth scroll |
| Навигация | Прямое открытие, refresh, back/forward, старые URL, якоря, смена языка на проекте |
| Загрузка | Первый визит без кэша, повторный визит, замедленный переход, ошибка загрузки |
| Окружение | Один закреплённый браузер для screenshot-diff; smoke-проверки Chromium, Firefox и WebKit |

Минимальный набор автоматических сравнений: главная, оба проекта и 404 × три языка × две темы × три основных viewport. Пограничные ширины проверять для затронутых компонентов, а интерактивные состояния — отдельными сценариями.

Правила сравнения:

1. Снимать старую и новую версии в одинаковой среде с одинаковыми данными, локалью, темой и положением прокрутки. Зафиксировать время для динамического года в Footer.
2. Дождаться загрузки шрифтов и изображений, прокрутить к проверяемой секции и дождаться завершения её reveal-анимации.
3. Для статических кадров одинаково фиксировать фазу бесконечных анимаций в обеих версиях. Отключение анимации не должно оставлять Motion-элементы в исходном скрытом состоянии.
4. Движение, тайминги, hover и переходы темы дополнительно проверять в обычном режиме. Статический screenshot не подтверждает эквивалентность анимаций.
5. Использовать попарное сравнение и overlay/diff. Разницу хэшей CSS Modules не считать визуальным дефектом; геометрия и вычисленные стили должны совпадать.
6. Допускать только объяснимый шум растеризации в одинаковой среде. Сдвиги элементов, изменение цветов, шрифтов и переносов строк требуют исправления; нельзя скрывать их повышением общего порога diff или маскированием секций.

## Критерии завершения архитектурной миграции

- [ ] Главная, обе страницы проектов и 404 визуально соответствуют исходной версии во всех обязательных сочетаниях темы, языка и viewport.
- [ ] Сохранены контент, порядок элементов, шрифты, SCSS-токены, breakpoint-условия и изображения.
- [ ] Сохранены состояния меню, навигация, переключатели, прокрутка и анимации.
- [ ] Нет вспышки неверной темы, неверных скриншотов, новых сдвигов layout и ошибок гидратации.
- [ ] Next.js App Router, next-intl и структура FSD используются в рабочем приложении.
- [ ] Проекты получаются через серверный интерфейс, независимый от внешнего источника.
- [ ] Проходят production build, проверка типов, lint и проверки основных сценариев; существующие исключения явно задокументированы.
- [ ] Проверены preview-развёртывание, совместимость старых ссылок и возможность отката.

Подключение внешнего источника и последующие оптимизации имеют собственную приёмку. Завершение этапов 0–5 означает достижение текущего приоритета: новая архитектура при сохранении внешнего вида.
